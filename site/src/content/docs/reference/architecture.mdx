## Retrieval

<Figure src={pipeline} dark={pipelineDark} alt="Scholar MCP retrieval pipeline" width={720} />

A search has four steps.

1. **Ask every source.** Your question goes to all scholarly sources at once, in the form each one searches best, from meaning-based indexes to keyword catalogues.
2. **Gather without waiting.** Sources answer at their own pace and no slow source holds up the others. A source that answers late still counts.
3. **Rank, then follow the evidence.** The most relevant papers bring in their references, citations and related work, so you also get papers your words did not name.
4. **Rank everything together.** All candidates are ordered as one pool, and filters and the result limit apply only to that final order.

The order rests on how well each paper answers the question, and also weighs citations, how many sources found it and how recent it is. These are ranking signals, not judgements of a paper's quality. `sort` orders by citation count or date instead, and `intent` leans the search toward foundational work, recent work, surveys, methods or datasets.

## One paper, one entry

The same paper often arrives from several sources under different identifiers: a DOI, an arXiv version, a PubMed ID or only a title. Scholar recognises them as one work, keeps the most complete metadata from each, and remembers which sources found it. A preprint and its published version share one entry, and duplicate uploads of the same paper never take several places in your results.

## Sources and models

Each source states what it can do, from search and paper lookup to citations, references and PDFs, so a new source makes Scholar broader without adding tools for your agent to learn. Crossref, Europe PMC, INSPIRE-HEP, Semantic Scholar and OpenAlex together supply the citation graph.

A source that fails is reported separately from one that found nothing, so an empty answer is never mistaken for no papers. Ranking runs on the cloud Qwen model, a compatible service you choose, or a local model when neither is available; an unreachable service is skipped for a few minutes instead of slowing every search, see [Configuration](/scholar-mcp/configuration/#reranker).

## Runtime

<Figure src={runtime} dark={runtimeDark} alt="Scholar MCP runtime architecture" width={720} />

A client on your machine connects over stdio, which means it starts Scholar itself and talks to it through standard input and output, with no network port. When a client cannot start a program, such as an agent in a web page or a server several people share, Scholar runs as a network service and clients connect over Streamable HTTP. A local SQLite library handles full-text search, PDF attachments, JSONL snapshots and the Obsidian, Zotero and Notion connectors. Full text comes from open copies first and, for licensed papers, through your library's proxy.

Tools answer in readable YAML for the model and structured data for the client. Any identifier a tool returns, a paper link or an exact title works in every other tool.

## Reading and keeping papers

`read_paper` reads a paper without keeping a copy, unless you already downloaded it. By default pages 1 to 10 come back as Markdown marked by page, up to 100,000 characters per response, so a typical ten-page read arrives whole. A longer range stops at a page boundary and returns `next_pages`. In Codex, which cuts the middle out of long results, reads stop near 36,000 characters and return `next_pages`. Page ranges reach later sections, figure, table and page names return images of that part, and recognised tables come back as structured text.

`download_paper` keeps the PDF in your papers folder and records it in a library collection. Each PDF is checked before it is kept, and the returned path is absolute, so later sessions find it from any directory. When a better version becomes available, such as the published version of a preprint, it is kept alongside the older file, so your annotations survive.

The library keeps records with the full author list and abstract, searchable in full text. Connectors export or sync only when you ask.

## Health

Twenty-odd outside services can change, rate-limit or go down at any time, so Scholar watches every link itself. Every tool call leaves one line in a small local record, without the question itself, with how long it took, how each source answered, which ranking model ranked and where a PDF came from. `scholar-mcp doctor` reads it and names a source that started failing, went quiet, lost its abstracts or slowed down. `doctor --network` probes the free links that real use has not exercised lately, see [CLI](/scholar-mcp/cli/#doctor).
